# Authoring against Tether's WIT interfaces

Tether exposes a WASI Preview 2 / Component Model interface so Wasm guests
can query/execute against Postgres, MySQL, and Redis, and perform key-value
operations against Redis, without depending on Tether's internal
`WireDriver` types. The interface is defined once, in
[`tether/wit/tether.wit`](../wit/tether.wit), and consumed from two sides:

- **Guest side** (your Wasm module): generated by
  [`wit-bindgen`](https://github.com/bytecodealliance/wit-bindgen).
- **Host side** (`tether/proxy`): generated by
  `wasmtime::component::bindgen!` in
  [`tether/proxy/src/component.rs`](../proxy/src/component.rs).

Both codegen paths point at the same `.wit` source, so the interface only
needs to change in one place.

## Available interfaces

- `tpt:tether/data` — `query`, `execute`, and a `transaction` resource
  (`query`/`execute`/`commit`/`rollback`). Works against whichever driver
  (Postgres, MySQL, Redis) the host has connected.
- `tpt:tether/kv` — `get`, `set`, `del`, `expire`. Only meaningful against a
  Redis-backed driver; calling these against a non-Redis driver returns
  `tether-error::unsupported-operation`.

**Not yet available**: pub/sub. A long-lived subscription doesn't map
cleanly onto WIT's synchronous call/return shape and needs its own streaming
design (`wasi:io/streams` or polling) — tracked as a backlog item in the
root `TODO.md` (Phase 10).

## Scaffolding a new guest

1. Add `wit-bindgen` to your guest crate's `Cargo.toml` (see
   [`tether/examples/wit-guest-demo/Cargo.toml`](../examples/wit-guest-demo/Cargo.toml)
   for a minimal example — `crate-type = ["cdylib"]`, and give the crate its
   own `[workspace]` table so it stays out of the root Rust workspace).
2. Generate bindings pointing at `tether/wit`:
   ```rust
   wit_bindgen::generate!({
       world: "tether-guest",
       path: "../../wit", // relative to your crate
   });
   ```
3. Call `tpt::tether::data::{query, execute, begin_transaction}` and
   `tpt::tether::kv::{get, set, del, expire}` from your guest code.
4. If your guest needs an entry point the host calls (like the demo's
   `run`), add an `export` function to the `tether-guest` world in
   `tether.wit` and implement the generated `Guest` trait (see
   `tether/examples/wit-guest-demo/src/lib.rs`).

## Build → adapt → load

`wit-bindgen`'s guest codegen targets Preview 1, so a compiled module needs
adapting into an actual component before the host can load it:

```sh
rustup target add wasm32-wasip1
cargo build --target wasm32-wasip1
wasm-tools component new target/wasm32-wasip1/debug/your_guest.wasm \
  --adapt wasi_snapshot_preview1=wasi_snapshot_preview1.reactor.wasm \
  -o your_guest.component.wasm
```

See [`tether/examples/wit-guest-demo/README.md`](../examples/wit-guest-demo/README.md)
for the full walkthrough, including where to get the adapter binary.

## How the proxy loads a component

`tether/proxy/src/component.rs` implements the host traits generated for
`data`/`kv`/`types` on `WitHostState`, a thin adapter over the existing
`WireDriver` enum (`tether/proxy/src/drivers/wire.rs` is untouched). To
instantiate a guest component:

```rust
let mut linker = wasmtime::component::Linker::new(&engine);
TetherGuest::add_to_linker(&mut linker, |state: &mut WitHostState| state)?;

let mut store = wasmtime::Store::new(&engine, WitHostState::new(driver));
let instance = TetherGuest::instantiate_async(&mut store, &component, &linker).await?;
```

See `tether/proxy/tests/component_test.rs` for a full working example.
