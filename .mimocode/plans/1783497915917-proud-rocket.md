# TPT Boxcar vs Docker: Competitive Analysis & Feature Gap Report

## Executive Summary

TPT Boxcar is a **real, functional platform** — not a prototype. The data planes (Tether wire drivers, Frontier proxy, Scope ingest pipeline) are production-grade with real protocol implementations. Origin has working process spawning, Wasm execution, containerd integration (Linux), bridge networking, DNS, crash recovery, and health checks.

**Unique advantages over Docker:**
- Native Wasm runtime (Wasmtime) alongside OCI — Docker has no native Wasm
- Multi-runtime manifest (OCI + Wasm + Process in one file) — Docker Compose is OCI-only
- Built-in observability (Scope) with eBPF tracing — Docker requires third-party tools
- AI-powered image analysis and migration (Chisel) — nothing like this exists in Docker
- Edge service mesh (Frontier) with Wasm plugins — Docker needs separate tooling (Traefik, Envoy)
- MCP server for AI agent integration — unique to Boxcar

**Critical gaps vs Docker:**
1. Port mapping is parsed but never enforced (no iptables/pf rules)
2. `exec` is a stub (prints only)
3. No Dockerfile build capability
4. No secrets management
5. No security profiles (seccomp, AppArmor, capabilities)
6. No rootless mode
7. OCI push not implemented
8. No log rotation or configurable log drivers
9. No resource limits for process/Wasm services
10. No file sync or watch mode for development

## Prioritized Improvement Roadmap

### P0: Critical (Blocks basic Docker replacement workflow)

1. **Port mapping enforcement** — `PortMapping` is parsed in manifest.rs but network.rs has no iptables/nftables/pf rule creation. Without this, services are unreachable from the host. Implementation: add `apply_port_mappings()` to NetworkManager that creates `iptables -t nat -A PREROUTING` rules (Linux), `pfctl` rules (macOS), or Windows port proxy.

2. **`tpt origin exec`** — Currently a print stub at `cli/main.rs:322-325`. Needs real implementation: for OCI services, use `ctr tasks exec` (already exists for health checks); for process services, use `tokio::process::Command` with PTY; for Wasm, not applicable.

3. **Dockerfile / image build** — Origin can only run pre-built images. Need a `tpt origin build` command that: parses a Dockerfile (or Boxcar-native build spec), executes multi-stage builds using containerd or buildkit, produces an OCI image. This is the biggest missing piece for a Docker replacement.

### P1: High Priority (Significant DX or security gaps)

4. **Resource limits for process/Wasm services** — `ResourceLimits` is parsed but only enforced for OCI via containerd cgroups. For process services: use `setrlimit`/cgroup v2 directly. For Wasm: Wasmtime's `ResourceLimiter` is already used in Frontier's plugin system — apply the same pattern to Origin's Wasm runtime.

5. **Secrets management** — Add `env_file:` directive to manifest schema (like Docker's `--env-file`). Support `.env` file loading. For production: add `secrets:` section that mounts Docker/K8s secrets as files.

6. **Security hardening** — Add `security:` section to manifest with `cap_add`/`cap_drop`, `read_only: true`, `no_new_privileges: true`. For OCI: pass `--cap-drop ALL --cap-add <specific>` to `ctr run`. For process: use Linux capabilities via `prctl`.

7. **File sync / watch mode** — Add `--watch` flag to `tpt origin up` that monitors source directories for changes and triggers service restart or hot-reload. Critical for developer iteration speed.

8. **Rootless mode** — Implement user namespace support so `tpt origin up` works without root. This is a significant architectural change (needs unprivileged network setup via `slirp4netns` or similar).

### P2: Medium Priority (Completes the Docker feature set)

9. **Log rotation and drivers** — Add `logging:` section to manifest with `driver`, `max_size`, `max_file`. Implement log rotation for OCI containers (use `logrotate` or in-process rotation).

10. **`tpt origin inspect`** — Show full service configuration, environment, volume mounts, network settings, health status, resource usage.

11. **`tpt origin stats`** — Live CPU/memory/network usage per service. For OCI: read cgroup stats via containerd. For process: read `/proc/<pid>/stat`.

12. **Health check for non-OCI services** — Process services could use HTTP/TCP health checks (open socket, check response). Wasm services could use a WASI-based health check interface.

13. **Compose feature parity** — Add variable interpolation (`${VAR:-default}`), `profiles:`, `extends:`, `build:` section, `configs:`, `secrets:` to manifest schema.

14. **OCI push** — Implement `tpt origin push` to push built images to registries. Needs token-based auth, not just anonymous.

15. **Image management** — `tpt origin images` (list), `tpt origin rmi` (remove), `tpt origin pull` (explicit pull command).

### P3: Low Priority (Nice-to-have)

16. **`docker events` equivalent** — Real-time event stream for lifecycle transitions.
17. **`docker cp` equivalent** — File copy to/from containers.
18. **IPv6 support** — Dual-stack networking, AAAA records.
19. **Overlay networks** — Multi-host networking (less relevant for local dev).
20. **tmpfs mounts** — In-memory filesystem for temp data.
21. **GPU/device passthrough** — For ML/AI workloads.
22. **`docker pause`/`unpause`** — Cgroup freezer integration.

## What Boxcar Does Better Than Docker

These are genuine competitive advantages worth marketing:

1. **Multi-runtime manifest** — One file runs OCI containers, Wasm modules, and native processes together. Docker Compose can only run OCI containers.

2. **Native Wasm execution** — Wasmtime integration with WASI support, signature verification, and replay capture. Docker has no native Wasm runtime.

3. **Built-in observability** — Scope provides OTLP-compatible tracing, metrics, and logs out of the box. Docker requires Datadog, Grafana, or similar third-party tools.

4. **AI-powered migration** — Chisel analyzes Docker images, generates SBOMs, scans for CVEs, and creates AI-assisted Wasm migration plans. Nothing like this exists in Docker.

5. **Edge service mesh** — Frontier provides load balancing, rate limiting, JWT auth, and Wasm plugins. Docker requires separate tools (Traefik, Nginx, Envoy).

6. **Database proxy** — Tether provides WIT-compatible database access for Wasm modules with connection pooling and TLS. Docker has no equivalent.

7. **Time-travel debugging** — Capture a Wasm invocation via Scope's eBPF probes and replay it offline. Docker has no equivalent.

8. **MCP integration** — All five products exposed as MCP tools for AI agents. Docker has no AI agent integration.

9. **Cross-product orchestration** — `boxcar.yaml` + `tpt up` orchestrates Tether + Origin + Frontier together with dependency ordering. Docker Compose is a single-product tool.

## Architecture Strengths Worth Preserving

- **Clean separation of concerns**: manifest → runtime → network → DNS → lifecycle → facade. Each layer is independently testable.
- **Honest platform gating**: Rather than faking OCI on non-Linux, the code returns hard errors. Network bridge creation falls back gracefully.
- **eBPF observability**: The Scope agent's real kernel probes (tcp_connect + syscall tracing) are a significant differentiator.
- **Wire-protocol drivers**: Tether's hand-written Postgres/MySQL/Redis drivers are impressive and avoid heavy dependencies.
- **Plugin system**: Frontier's Wasmtime plugin loader with hot-reload and resource limits is production-grade.

## Recommended Next Steps

1. **Fix port mapping** (P0) — This is the single biggest gap. Without it, Origin services can't be accessed from the host browser/CLI.
2. **Implement exec** (P0) — Developers need `docker exec` equivalent for debugging.
3. **Add resource limits for process/Wasm** (P1) — Critical for multi-tenant and CI environments.
4. **Add env_file support** (P1) — Low effort, high DX impact.
5. **Start build pipeline design** (P0) — This is the largest effort; start design before implementation.
