TPT Boxcar: Open Source Product Design Document
Executive Summary
The TPT Boxcar project addresses the critical tooling gap in the modern cloud-native landscape. While the underlying engines for containers and WebAssembly are mature, the developer experience, state management, observability, and edge routing tools remain highly fragmented and often locked behind proprietary paywalls. TPT Boxcar provides a unified, high-performance, and entirely free product line, released under the Apache 2.0 License. This suite is a public good designed to guide applications seamlessly from local development to the edge, democratizing access to next-generation infrastructure and ensuring the community retains full ownership of their tooling.
1. TPT Origin (The Unified Local Sandbox)
The "Anti-Docker Desktop"
Modern developers are trapped between two frustrating worlds when building locally. On one hand, they are forced to use heavy, resource-hogging container runtimes that consume gigabytes of RAM and require persistent background daemons just to run a simple local database. On the other hand, the rise of WebAssembly (Wasm) requires installing entirely separate, fragmented runtimes and struggling to network them together. TPT Origin solves this by providing a unified, ultra-lightweight local development environment that seamlessly orchestrates both OCI containers and Wasm modules side-by-side, completely eliminating the need for heavy background virtual machines.
At its core, TPT Origin is a daemonless, native binary built for speed and efficiency. When a developer runs a single command, it instantly spins up a mix of traditional containers (like Postgres or Redis) and Wasm microservices from a single, unified manifest file. Because it relies on native OS virtualization and eBPF for local networking rather than a persistent background daemon, it consumes a fraction of the system resources. It automatically creates a local service mesh, allowing a Wasm module to communicate with a containerized database via standard DNS with zero manual configuration, making the local environment feel like magic.
From a community perspective, TPT Origin acts as the ultimate on-ramp for next-generation development. By keeping the entire tool—including a beautiful, native desktop GUI built with Tauri—100% free and open source, it drastically lowers the barrier to entry for developers wanting to experiment with Wasm. It will spread organically through engineering organizations and universities, becoming the de facto standard for local hybrid development. As the entry point to the TPT ecosystem, it naturally guides users toward the rest of the suite as their applications scale, fostering a massive community of contributors who share manifests and local environment templates.
Tech Stack:
Core Engine: Rust (for memory safety, zero-cost abstractions, and high performance).
Container Runtime: Embeds containerd logic for OCI compliance without the Docker daemon.
Wasm Runtime: Embeds Wasmtime for fast, standards-compliant Wasm execution.
Networking: eBPF (via the Aya Rust library) for ultra-lightweight, kernel-level local routing and DNS resolution.
UI/CLI: Rust for the CLI, with a fully open-source Tauri desktop GUI for visual management.
2. TPT Tether (The State & Connection Proxy)
The "Missing Link" for Wasm
The single biggest technical blocker preventing the open-source community from adopting WebAssembly for backend microservices is state management. Wasm is strictly stateless and heavily sandboxed by design, making it incredibly inefficient at managing persistent TCP connections, such as those required to talk to a relational database. If a serverless Wasm function scales to 10,000 concurrent instances, it will attempt to open 10,000 separate database connections, instantly crashing the database server. TPT Tether solves this critical bottleneck by acting as an intelligent, lightweight sidecar proxy specifically engineered for Wasm workloads.
TPT Tether sits directly between the stateless Wasm applications and the stateful backend databases (Postgres, MySQL, Redis). It handles all the heavy lifting of TCP connection pooling, TLS termination, and database authentication, allowing thousands of Wasm instances to share a tiny, manageable pool of persistent database connections. Crucially, it exposes these database operations to the Wasm module using the WASI Preview 2 Component Model. This means the Wasm application doesn't need to know it's talking to a proxy; it interacts with the database as if it were a highly optimized, local, synchronous key-value store.
By solving the state problem under the Apache 2.0 license, TPT Tether unblocks backend Wasm adoption for the entire open-source ecosystem. It allows indie developers and massive enterprises alike to build highly scalable Wasm backends without relying on proprietary, closed-source serverless platforms. The project will rely on community contributions to rapidly expand its library of native database drivers, ultimately standardizing how stateful connections are handled in the Wasm ecosystem and making it a foundational piece of infrastructure for the next decade of cloud-native development.
Tech Stack:
Core Proxy: Rust using the Tokio async runtime for massive concurrency with minimal overhead.
Database Drivers: Native, highly optimized Rust drivers (e.g., sqlx for Postgres, redis-rs).
Wasm Interface: WASI Preview 2 and the WIT (Wasm Interface Type) definition language to define the contract between the proxy and the Wasm module.
Control Plane: Go for the configuration API, integrating with Kubernetes ConfigMaps or Consul for dynamic routing rules.
3. TPT Scope (Hybrid eBPF Observability)
The Open Observability Standard
Observability in modern, hybrid cloud environments is a fragmented and expensive nightmare, often locking teams into proprietary SaaS platforms. When a user request bounces between an Nginx container, a Go microservice, a Wasm function, and a database, tracing that journey traditionally requires developers to inject heavy, language-specific SDKs into every single piece of code. TPT Scope completely disrupts this paradigm by utilizing eBPF (Extended Berkeley Packet Filter) to trace network traffic, system calls, and execution metrics directly at the Linux kernel level, providing complete, distributed tracing with absolutely zero code changes required from the development team.
Because TPT Scope operates entirely within the kernel, it is completely runtime-agnostic. It doesn't care if the process it is monitoring is a bloated Docker container, a lightweight Wasm module, or a bare-metal binary; it sees all traffic and system interactions uniformly. The data collection agent hooks into kernel tracepoints and exports the data using the industry-standard OpenTelemetry (OTel) protocol. Furthermore, it includes specialized instrumentation for Wasm runtime events—such as compilation time, instantiation latency, and memory paging—which traditional APM tools completely miss, giving developers unprecedented visibility into their Wasm workloads.
The true value of TPT Scope lies in democratizing enterprise-grade observability. By providing a completely free, open-source eBPF agent and a self-hostable dashboard, it allows any team—from solo indie hackers to massive universities—to monitor their infrastructure without paying exorbitant per-gigabyte ingestion taxes to third-party vendors. The community can freely fork the dashboard, build custom visualizations, and share OpenTelemetry configurations, creating a shared, vendor-neutral knowledge base of cloud-native performance metrics that belongs entirely to the public.
Tech Stack:
Data Collection Agent: Rust or Go utilizing eBPF (using Cilium/ebpf or Aya) to hook into kernel tracepoints.
Data Standardization: OpenTelemetry (OTel) protocol for exporting traces, metrics, and logs.
Backend Storage: ClickHouse or Apache Druid (columnar databases optimized for massive, high-speed time-series telemetry ingestion).
Frontend Dashboard: React and TypeScript, utilizing D3.js or Cytoscape for rendering complex, interactive service dependency graphs.
4. TPT Chisel (Automated Distiller & Migrator)
The "Bloat Sculptor"
The vast majority of container images in production and open-source registries are bloated, insecure, and slow to deploy. Developers frequently start with massive base images like ubuntu:latest, install unnecessary dependencies, and end up with 1.5GB containers that are riddled with CVEs and take minutes to pull from a registry. TPT Chisel is an automated CI/CD tool designed to "sculpt" these bloated images. It analyzes the actual runtime behavior of the application and chips away the unused 95% of the operating system, creating ultra-secure, tiny, distroless images in a matter of minutes.
The magic of TPT Chisel happens in two distinct phases. First, it runs the container in a secure sandbox and uses eBPF to trace exactly which files, libraries, and system calls the application actually touches during execution. It then constructs a brand-new image containing only those exact dependencies. In the second phase, the tool analyzes the compiled binary inside the container. If it detects a language that compiles cleanly to WebAssembly (like Rust, Go, or C++), it automatically triggers a cross-compilation pipeline to output a .wasm file, effectively migrating the workload from a container to Wasm without manual developer intervention.
TPT Chisel directly benefits the global open-source ecosystem by drastically reducing the storage and bandwidth footprint of public container registries. By providing this tool as a free GitHub Action and GitLab CI plugin, it raises the security baseline of the entire community, automatically patching CVEs by removing unused code and generating comprehensive Software Bills of Materials (SBOMs). It empowers maintainers of open-source projects to distribute incredibly lean, secure, and fast-loading artifacts to their users, while seamlessly feeding optimized Wasm modules into the rest of the TPT suite.
Tech Stack:
Core Engine: Go (excellent for interacting with Docker/OCI registry APIs and building CI/CD plugins).
File Tracing: eBPF (to monitor open(), read(), and exec() syscalls during the profiling run).
Wasm Compilation: Integration with WASI SDK, Emscripten, and language-specific Wasm targets (e.g., wasm32-wasi for Rust).
AI/Analysis Layer: Integration with local, open-weight LLMs (like Llama 3) to analyze source code and identify non-Wasm-compatible dependencies, suggesting automated refactoring paths without sending code to external APIs.
5. TPT Frontier (Wasm-Native Edge Service Mesh)
The Open Edge Gateway
As the community rushes to adopt WebAssembly for its speed and security, they face a major infrastructure hurdle: the tooling for routing, load balancing, and securing Wasm traffic at the edge is practically non-existent outside of massive, proprietary cloud providers. If a developer wants to run Wasm on their own AWS, GCP, or cheap bare-metal VPS infrastructure, they are forced to use heavy, memory-hungry proxies like Envoy that were designed for traditional containers. TPT Frontier solves this by providing an ultra-lightweight, self-hosted API Gateway and Service Mesh built from the ground up specifically for Wasm workloads.
TPT Frontier is a high-performance data plane written in Rust, utilizing asynchronous network I/O to handle massive throughput with minimal latency. Its defining feature is that it uses Wasm for its own plugin system. Developers can write custom routing rules, JWT validation, rate-limiting algorithms, or authentication logic in their language of choice, compile them to Wasm, and hot-load them into the gateway without ever restarting the proxy. This allows for unprecedented flexibility and speed, as the routing logic executes in microseconds within the same sandboxed environment as the application itself.
TPT Frontier gives the open-source community the performance benefits of edge computing without the vendor lock-in of proprietary edge clouds. It allows indie developers, small startups, and university research teams to build Cloudflare-like, globally distributed architectures on commodity hardware. By implementing the open xDS API standard for its control plane, it integrates seamlessly into existing open-source service meshes like Istio or Consul, ensuring that TPT Frontier acts as a neutral, community-owned building block for the future of distributed computing.
Tech Stack:
Data Plane (The Proxy): Rust, utilizing Hyper (HTTP library) and Tokio for asynchronous network I/O.
Plugin Execution: Embedded Wasmtime or WasmEdge to execute user-defined Wasm plugins safely and rapidly.
Control Plane: Go or Rust, implementing the open xDS API so it can integrate seamlessly into existing Istio or Consul service meshes.
Plugin SDK: TypeScript (using AssemblyScript) and Rust SDKs, allowing developers to easily write and compile their custom gateway logic.
The TPT Ecosystem Flywheel (The Open Source Loop)
The true power of TPT Boxcar is how the projects feed into a self-sustaining, community-driven loop:
A developer downloads TPT Origin to build their app locally, enjoying a frictionless, bloat-free experience.
They push their code, where TPT Chisel automatically shrinks their images and migrates compatible microservices to Wasm in their CI/CD pipeline.
They deploy to production, spinning up TPT Tether and TPT Frontier on their own Kubernetes cluster or bare-metal servers to handle traffic and state securely.
TPT Scope monitors the entire pipeline via eBPF, providing deep telemetry without requiring expensive SaaS subscriptions.
The Community Benefit: Because everything is Apache 2.0, other developers can build hosting companies, managed service providers, or consulting firms on top of the TPT stack. The core tooling remains forever free, vendor-neutral, and controlled by the community, ensuring that the transition from legacy containers to WebAssembly benefits everyone, not just a single corporation.
